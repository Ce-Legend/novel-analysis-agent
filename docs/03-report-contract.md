# 报告结构和质量检查

这个工具最后生成的是拆书报告。报告内容比普通摘要更细，核心是让读者能看到结构、节奏、人物关系和写法。

## 顶层模块

当前报告会按这个顺序输出：

1. 综述
2. 核心亮点总结
3. 核心卖点
4. 推荐定位
5. 剧情看点分层
6. 核心梗
7. 作品名、简介、章节名分析
8. 人物小传
9. CP 感分析
10. 剧情大纲
11. 开篇文法分析
12. 情感线
13. 章节细纲
14. 文笔内容总结

这个顺序来自真实拆书成品的使用习惯：先看作品整体能不能成立，再看人物和关系，最后进入章节级拆解。

## 章节细纲

章节细纲里保留这些字段：

- 剧情
- 危机
- 伏笔
- 悬念
- 高潮
- 爽点
- 情节点与节奏
- 名场面与金句
- 情感推进
- 文风信号

我最在意的是 `剧情` 和 `情节点与节奏`。如果这两块只剩短标签，整份拆书报告会很空。

## CP 感分析

CP 感不能只写一句总评。当前会拆成专题，比如：

- 初期建设
- 试探拉扯
- 权力博弈
- 身体记忆
- 外部催化
- 终局确认

每个专题都要尽量给支撑桥段。这样读者可以判断分析是否有文本依据。

## 质量检查会看什么

`quality_review.json` 会检查：

- Docx 和 PDF 是否真实生成。
- 顶层模块顺序是否稳定。
- 报告里有没有内部字段。
- 人物小传是否达到人物卡结构。
- CP 感分析是否有足够专题。
- 情感线是否有阶段锚点。
- 章节细纲数量是否匹配。
- 文笔模块有没有拆解维度。
- 是否存在弱占位、残句、截断尾巴。

这一步不能保证报告一定好，但能帮我提前挡住很明显的交付问题。

## 为什么保留 mock provider

mock provider 有两个作用。

第一，它让别人不填 Key 也能跑完整链路，看到目录结构和导出效果。

第二，它让测试更稳定。报告渲染、断点续跑、运行锁、导出格式这些能力，不应该依赖真实模型是否稳定。
