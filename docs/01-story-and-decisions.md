# 从一次拆书交付长出来的工具

这个项目最有意思的地方，不在于它能调用模型，而在于它被真实交付一点点逼出了工程形状。

一开始我只想让模型把小说拆成大纲、章节细纲、情感线和文笔总结。很快就发现，长篇文本的难点会集中在三处。

第一处是输入太长。一本长篇小说直接塞给模型，前半段和后半段的颗粒度很难稳定。模型会记得大的情节方向，但很容易丢掉章节级变化。

第二处是报告太复杂。拆书报告和普通读后感差别很大，它有很多固定栏目：核心亮点、卖点、推荐定位、剧情看点、人物小传、CP 感分析、主线大纲、情感线、章节细纲、文笔内容总结。只要其中一块变成空话，整份报告的可信度就会掉。

第三处是交付要可复查。一次长任务跑几个小时后，如果只剩最终 PDF，后面很难判断问题出在切章、章节抽取、全书聚合，还是导出层。于是我开始把每一步都落盘。

最后形成的思路很朴素：不要追求一次生成完美答案，先把长文本拆成能检查的小单元，再逐层合并。

## 我后来保留了哪些设计

### 章节级抽取先行

每一章先抽取结构化信息：剧情事件、危机、伏笔、悬念、高潮、爽点、情节点与节奏、情感状态、角色关系、文风信号。

这样做的好处是，后面的全书聚合有了更稳定的材料来源。即使全书汇总写得不好，也能回到章节 JSONL 里查原因。

### 全书聚合单独处理

章节级结果适合细节，全书级结果适合组织。这个项目里，全书聚合会重新整理：

- 故事整体概览。
- 核心卖点。
- 推荐定位。
- 主线大纲。
- 情感线阶段。
- 人物卡。
- CP 专题。
- 文笔拆解。

我实践下来比较喜欢把长上下文模型只放在全书聚合层。这样成本更可控，失败范围也更小。

### 导出层统一 AST

Markdown、Docx、PDF 共用同一份报告结构。这个改动很关键。

早期如果每种格式各写一套导出逻辑，很容易出现 Markdown 有 A 模块，PDF 顺序变了，Docx 又漏一个字段。统一结构以后，导出层只负责渲染。

### 质量检查不能省

真实报告最怕几类问题：

- 出现内部字段，比如 `chapter_id`。
- 出现看起来没写完的残句。
- 模块标题有了，内容很空。
- 前几章很细，后几章突然变粗。
- PDF 和 Docx 顺序跟 Markdown 不一致。

所以我把 `quality_review.json`、`delivery_integrity_review.json`、`reference_alignment_review.json` 都留了下来。它们不追求替代人工判断，但能先挡住很多明显问题。

## 这个 repo 适合怎么参考

如果你也想做长文本分析工具，可以直接参考这几个点：

- 长文本不要只靠一次总 prompt。
- 每个阶段都留下机器可读产物。
- 导出报告前做一次自动巡检。
- mock provider 要保留，方便没有 Key 时跑通全链路。
- 真实模型接入和报告渲染要解耦。
